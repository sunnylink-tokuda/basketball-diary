# チャッピーの設定・検証

ガード指導・過去日記の成長分析を追加する場合は、[追加の反映手順](chappy-growth-setup.md)を先に確認してください。以下は初期版の説明です。追加版では所有者登録が必要となり、保存済み助言を編集後も維持する動作に変わります。

この変更は `feature/chappy-advice` 用です。mainへのマージ・本番DB変更・Functionの本番デプロイは別途行ってください。

## 既存データの前提

既存アプリは `public.records(date, data, updated_at)` を使う共有日記です。利用者ごとの所有者列やログイン画面はありません。家族専用アプリとして、ログイン認証は親も子も使わないことにしました（ログインなし化の変更で確定）。AI（チャッピー）もログインなしで動き、Edge Functionはアプリのanonキーだけを確認し、所有者対応表から決まる家族のユーザーIDの範囲で日記を読みます。複数家庭を同じプロジェクトで扱う設計ではありません。

ステージングで、records.dateがtext型の一意キー、dataがJSON/JSONB型であること、既存のRLS・GRANTがログイン後の保存にも対応することを確認してください。リポジトリには既存DBのDDLがないため、本番スキーマ・ポリシーを検証したとは扱わないでください。既存recordsの権限はこのSQLで変更しません。

## ステージングへの適用

1. Supabaseのステージングプロジェクトを用意し、既存recordsの構造とテスト用日記をコピーします。SQL Editorで `supabase/chappy-advice.sql` を一度だけ実行してください。CLIの導入がこの実行環境で失敗したため、このファイルはCLI生成のmigrationではなく、レビュー可能なセットアップSQLです。
2. ログイン用アカウントは不要です。所有者対応表（`chappy_record_owners`）に既存の日記の所有者が登録されていることを確認してください（登録方法は [追加の反映手順](chappy-growth-setup.md)）。あわせて `supabase/chappy-no-login.sql` を適用し、家族のユーザーID解決（`chappy_family_user`）とログインなし保存時の所有者自動登録を有効にします。
3. Edge FunctionsのSecrets画面に `OPENAI_API_KEY` を登録します。未設定の場合、Functionは拒否します。任意の `OPENAI_MODEL` の既定値は `gpt-4o-mini` です。キーはSupabaseのSecrets画面で入力し、ソースコード・GitHub・VITE環境変数・ターミナル履歴には入れないでください。旧 `CHAPPY_ALLOWED_USER_IDS` は不要になったので削除して構いません。
4. CLIの `supabase --help` / `supabase functions deploy --help` を確認し、ステージングをリンクして `supabase functions deploy chappy-advice` でデプロイします。`verify_jwt = true` を維持してください（anonキーもJWTとして検証されます）。`SUPABASE_URL`、`SUPABASE_ANON_KEY`、`SUPABASE_SERVICE_ROLE_KEY` はEdge Functionの標準サーバー環境変数を使い、ブラウザーには渡しません。
5. フロントエンドの既存 `VITE_SUPABASE_URL` と `VITE_SUPABASE_ANON_KEY` はステージングの公開用キーを設定します。`npm ci` / `npm test` / `npm run build` で確認できます。

## 動作

- 日記のDB保存が成功したあと、詳細画面が保存済みの日記についてFunctionを呼びます。ログインは不要で、開けばすぐ生成します。保存失敗時は入力を残し、AIを呼びません。
- FunctionはAuthorizationのanonキーを確認し、家族のユーザーIDをサーバー側で解決します。ブラウザーから受け取るのは日付と操作だけです。日記本文はサーバーがrecordsから読みます。
- 練習・試合・振り返りのフィールドだけをOpenAIに送ります。チーム名、対戦相手、お小遣い、保護者コメントは送信対象から外します。自由記述に個人情報を書くと、その自由記述には含まれるため、氏名や連絡先を書かないでください。
- 小学5年生向けの3項目を各120文字以内で検証し、別テーブルchappy_adviceに保存します。既存recordsのJSONをAIで上書きしません。生成した内容はReactのテキストとして表示します。
- 同じ保存内容はキャッシュを返します。日記変更後は古い結果を返さず、生成中に内容が変わっても古い結果を保存しません。日記を削除すると対応するアドバイスも削除されます。
- 1日・許可ユーザーごとに生成開始を最大30回に制限します。同一日記の再試行には60秒の間隔を設けます。生成は25秒でタイムアウトし、失敗時も日記は残ります。画面から再試行できます。OpenAI側でも予算制限を設定してください。
- 表示するたびに未生成分を補える設計です。ブラウザーを閉じた場合は次に詳細画面を開いた際に再試行できます。常時バックグラウンドで動作するジョブではありません。

## 確認項目

ステージングでは、ログインなしで日記保存→生成中→3項目表示→再読み込み後も保存結果が表示されることを確認します。別の日に移動しても結果が混ざらないこと、編集で更新されること、APIの失敗時も日記が残ること、anonキーでないリクエストが生成できないことも確認してください。

SQLはローカルのPostgres互換エンジンPGliteでキャッシュ・競合・利用制限・RLS/権限・削除連動を検証します。本番SupabaseのAdvisorsと実際のAuth・OpenAI呼び出しは、ステージング適用後に確認してください。

## ログイン・パスワード再設定の廃止について

ログインなし化の変更で、メール＋パスワードのログイン、チャッピー欄のパスワード設定・変更、パスワード再設定メール（回復リンク）への対応はすべて廃止しました。フロントエンドからログイン画面と再設定画面（`RecoveryGate` / `passwordRecovery`）を取り除き、Supabaseクライアントはanonキーだけを使う素のクライアントにしています。

- Supabase Authのアカウントや再設定メールは、アプリの利用にはもう必要ありません。Site URL / Redirect URLsなどのAuth URL設定も変更不要です。
- Edge FunctionはユーザJWTと許可リスト（旧 `CHAPPY_ALLOWED_USER_IDS`）を使いません。Secretsから削除して構いません。
- 過去の所有者対応表・保存済みアドバイスはそのまま使えます。所有者は `chappy_family_user`（最も多く日記を持つユーザー）として解決されます。
