# チャッピーの設定・検証

この変更は `feature/chappy-advice` 用です。mainへのマージ・本番DB変更・Functionの本番デプロイは別途行ってください。

## 既存データの前提

既存アプリは `public.records(date, data, updated_at)` を使う共有日記です。利用者ごとの所有者列やログイン画面はありません。今回はこの共有モデルを維持し、AIだけをSupabase Authとサーバーの利用者許可リストで保護します。許可された利用者は、この共有日記全体をAIで読み取れます。複数家庭を同じプロジェクトで扱う設計ではありません。

ステージングで、records.dateがtext型の一意キー、dataがJSON/JSONB型であること、既存のRLS・GRANTがログイン後の保存にも対応することを確認してください。リポジトリには既存DBのDDLがないため、本番スキーマ・ポリシーを検証したとは扱わないでください。既存recordsの権限はこのSQLで変更しません。

## ステージングへの適用

1. Supabaseのステージングプロジェクトを用意し、既存recordsの構造とテスト用日記をコピーします。SQL Editorで `supabase/chappy-advice.sql` を一度だけ実行してください。CLIの導入がこの実行環境で失敗したため、このファイルはCLI生成のmigrationではなく、レビュー可能なセットアップSQLです。
2. Supabase Authで保護者などのメールアドレス・パスワード付きアカウントを用意します。画面は `signInWithPassword` を使い、自動サインアップやMagic Link送信はしません。初回パスワード設定は下の手順を参照してください。
3. Edge FunctionsのSecrets画面に `OPENAI_API_KEY` と `CHAPPY_ALLOWED_USER_IDS` を登録します。後者はAuth画面で確認した許可ユーザーUUIDのカンマ区切りです。未設定の場合、Functionは拒否します。任意の `OPENAI_MODEL` の既定値は `gpt-4o-mini` です。キーはSupabaseのSecrets画面で入力し、ソースコード・GitHub・VITE環境変数・ターミナル履歴には入れないでください。
4. CLIの `supabase --help` / `supabase functions deploy --help` を確認し、ステージングをリンクして `supabase functions deploy chappy-advice` でデプロイします。`verify_jwt = true` を維持してください。`SUPABASE_URL` と `SUPABASE_SERVICE_ROLE_KEY` はEdge Functionの標準サーバー環境変数を使い、ブラウザーには渡しません。
5. フロントエンドの既存 `VITE_SUPABASE_URL` と `VITE_SUPABASE_ANON_KEY` はステージングの公開用キーを設定します。`npm ci` / `npm test` / `npm run build` で確認できます。

## 動作

- 日記のDB保存が成功したあと、詳細画面が保存済みの日記についてFunctionを呼びます。AIにログインしていない場合はログイン案内を表示し、ログイン後に生成します。保存失敗時は入力を残し、AIを呼びません。
- FunctionはAuthのユーザーを検証し、Secretの許可リストを確認します。ブラウザーから受け取るのは日付と操作だけです。日記本文はサーバーがrecordsから読みます。
- 練習・試合・振り返りのフィールドだけをOpenAIに送ります。チーム名、対戦相手、お小遣い、保護者コメントは送信対象から外します。自由記述に個人情報を書くと、その自由記述には含まれるため、氏名や連絡先を書かないでください。
- 小学5年生向けの3項目を各120文字以内で検証し、別テーブルchappy_adviceに保存します。既存recordsのJSONをAIで上書きしません。生成した内容はReactのテキストとして表示します。
- 同じ保存内容はキャッシュを返します。日記変更後は古い結果を返さず、生成中に内容が変わっても古い結果を保存しません。日記を削除すると対応するアドバイスも削除されます。
- 1日・許可ユーザーごとに生成開始を最大30回に制限します。同一日記の再試行には60秒の間隔を設けます。生成は25秒でタイムアウトし、失敗時も日記は残ります。画面から再試行できます。OpenAI側でも予算制限を設定してください。
- 表示するたびに未生成分を補える設計です。ブラウザーを閉じた場合は次に詳細画面を開いた際に再試行できます。常時バックグラウンドで動作するジョブではありません。

## 確認項目

ステージングでは、メールアドレス＋パスワードでログイン後に日記保存→生成中→3項目表示→再読み込み後も保存結果が表示されることを確認します。別の日に移動しても結果が混ざらないこと、編集で更新されること、APIの失敗時も日記が残ること、未ログイン・許可外ユーザー・匿名ユーザーが生成できないことも確認してください。

SQLはローカルのPostgres互換エンジンPGliteでキャッシュ・競合・利用制限・RLS/権限・削除連動を検証します。本番SupabaseのAdvisorsと実際のAuth・OpenAI呼び出しは、ステージング適用後に確認してください。

## メール＋パスワードへの切り替え手順

今回のログイン修正では、SQLの再実行やEdge Functionの再デプロイ、Secretの変更は不要です。変更ブランチのフロントエンドをプレビュー・デプロイしてください。mainへのマージは不要です。

1. Supabaseの対象プロジェクトを開き、AuthenticationのSign In / Providers（画面によってはProviders）でEmailが有効になっていることを確認します。メール確認を無効にする必要はありません。
2. パスワードがすでにある利用者は、そのメールアドレスとパスワードでログインするだけです。
3. Magic Linkだけを使っていた利用者がまだログイン中なら、日付の詳細画面を開き、チャッピー欄の「パスワードを設定・変更」を押します。「新しいパスワード」と確認欄に同じものを入力し、「パスワードを保存」を押します。8文字以上で、Supabase側のパスワード条件にも合わせてください。
4. ログインしておらず、パスワードもない場合は、Authentication → URL ConfigurationのSite URLを変更ブランチのサイトURLに設定します。Redirect URLsにもそのURLを登録します。Authentication → Usersで**既存の利用者**を選び、パスワード再設定メールを送る操作（Reset password / Send password recovery）を使います。届いたリンクを開くと、認証確認後に「パスワードの再設定」画面が自動表示されます。新しいパスワードと確認欄を入力して保存し、「カレンダーへ進む」を押してください。日付の選択は不要です。標準のSupabaseメールテンプレートのConfirmationURLを使う想定です。カスタムテンプレートが別の未実装パスへ送る場合は設定を見直してください。
5. 初回の再設定メールにもメール送信制限はかかります。制限中なら解除を待って一度だけ送り、繰り返し送らないでください。通常のパスワードログインではログインメールを送りません。
6. 既存利用者を削除・作り直す必要はありません。同じユーザーUUIDを使うので、SecretのCHAPPY_ALLOWED_USER_IDSはそのままです。新しいアカウントを作った場合だけ、新しいUUIDを許可リストへ登録します。
7. 一度ログアウトし、メールアドレス＋パスワードでログインしてアドバイスが出ることを確認します。ページを再読み込みしてもログイン状態が続くことと、ログアウトすると入力欄に戻ることを確認してください。

Supabase SDKがブラウザーのlocalStorageにセッションを保持し、トークンを自動更新します。アプリはパスワードそのものをlocalStorageやDBへ保存しません。ブラウザーの保存データを削除した場合やセッションが失効した場合には、再ログインが必要です。保護者の管理下にある端末で利用してください。

パスワードをこのチャットやGitHubには貼らないでください。パスワード設定時に再認証を求められる設定なら、再ログイン直後または新しい再設定リンクから実施してください。

参考: [Supabaseのパスワード認証](https://supabase.com/docs/guides/auth/passwords)、[signInWithPassword](https://supabase.com/docs/reference/javascript/auth-signinwithpassword)。

## 回復メールから直接フォームを開く修正

以前はAuth監視が日付の詳細画面のチャッピー欄にしかなく、PASSWORD_RECOVERYを専用画面への切り替えに使っていませんでした。今回、アプリ起動時からイベントを監視し、SDKの認証初期化中にはApp（カレンダーや日記読込）をマウントしないようにしました。SDKがURLを消す前に回復リンクの種類を控え、マウント前・初期化直後に届く回復イベントも処理します。新しい回復リンクは後述のURL形式ごとのAuth APIで検証し、その成功応答を必要とします。通常の保存済みログイン状態だけで回復フォームを有効にはしません。

同じタブで更新しても未完了のフォームを表示するため、sessionStorageには「pending」という画面状態だけを記録します。トークンやパスワードは記録しません。Safari等でsessionStorageが利用できなくても、そのページ内の認証処理とフォーム表示は継続します。更新後の状態保持は、保存領域が利用できる場合だけです。入力欄は16px以上にしてiPhone Safariの入力時拡大を抑えています。

Vercelでこのブランチの最新プレビューをデプロイした後、次の順で確認してください。

1. SupabaseのSite URLとRedirect URLsが、今回使うテスト用Vercel URLになっているか確認します。メールテンプレートは標準のConfirmationURLを使用できます。token_hash形式のカスタムリンクも、アプリのルートURLにtype=recoveryとtoken_hashを付けた形式なら処理できます。
2. SupabaseのUsers画面から新しいパスワード再設定メールを一度送り、最新のリンクをiPhoneのSafariで開きます。認証確認中の表示の後に、カレンダーではなく2つのパスワード入力欄が出ることを確認します。
3. 同じパスワードを入力して保存します。「カレンダーへ進む」から日記を開き、アドバイス表示を確認します。ログアウト後、新しいパスワードで通常ログインも確認します。
4. 期限切れ・使用済みリンクの場合は、専用のエラー表示から新しいメールのリンクを利用します。URLやメールのリンクには認証情報があるため、このチャットやGitHubに貼らないでください。

この修正はフロントエンドだけです。既存の日記データ、SQL、Edge Function、Secret、許可ユーザーリストは変更せず、再適用も不要です。自動テストでは認証前の待機、イベント到着の順序違い、Safariで保存領域が使えない場合、更新、期限切れ、不一致、保存失敗と成功を確認します。実機のSafariと実際の回復メール・Supabase設定は上の手順で確認してください。

## 新しいメールのリンクでも認証エラーになる場合の修正

回復イベントの到着順だけで判定する処理を廃止し、URLごとにAuth APIを一度だけ呼ぶようにしました。回復コールバックではSDKの自動URL処理を無効にして、同じワンタイムトークンの二重消費を防ぎます。SDKがSIGNED_INだけを通知する場合も、検証済みのAPI応答からフォームを表示します。

- `#access_token=...&refresh_token=...&type=recovery`、またはクエリに同じ項目がある場合: `setSession` で検証します。トークンの有効期限やユーザー確認はSupabase SDKとAuth APIが処理します。
- `?token_hash=...&type=recovery`: `verifyOtp` をrecoveryタイプで一度呼びます。
- `?code=...`（任意の `sb_flow_id` を含む場合も対応）: `exchangeCodeForSession` を一度呼びます。PKCE用verifierが、再設定を開始したブラウザーの保存領域に必要です。PCで開始してSafariで開く場合など、verifierがないコードをアプリだけで復元することはできません。
- 認証用パラメータが欠けたリンク、使用済み・期限切れ、PKCE情報不足、通信エラーは区別して表示します。以前の通常セッションへのフォールバックはしません。トークンはコールバックの開始時にURLから取り除き、Auth API処理後に一時変数からも取り除きます。生のエラー本文・URL・トークンはログに出しません。

### メール再送なしで検証する

`npm ci` → `npm test` → `npm run build` で確認できます。`tests/recovery-sdk.test.ts` はリポジトリで使う本物のSupabase SDKに対し、AuthのHTTP応答だけをテスト内で置き換えます。架空のトークンとユーザーで各URL形式、SIGNED_IN通知、保存領域が使えないケース、期限切れ、PKCE verifier不足を再現します。メール送信APIや実際のSupabaseネットワークにはアクセスしないため、メール制限を消費しません。実機Safariと本番設定のテストではありません。

### Vercelでの確認

最新のfeature/chappy-adviceをプレビューに反映してください。SDKの公開キーとURLが、再設定メールを送ったSupabaseプロジェクトに対応していることも確認します。Site URLとRedirect URLsの再設定だけでは、別プロジェクトのキーやURLの不一致は解消しません。

通信エラーの場合は接続状態を確認してください。真に期限切れ・使用済みのワンタイムトークンはこの修正では再利用できません。メールを繰り返し送らず、制限が解除された後に一度だけ新しいリンクで確認してください。PCとSafariをまたぐPKCEが必要な場合は、標準ConfirmationURLの回復フローかtoken_hash形式のテンプレートを検討してください。

調査のために共有する場合も、URLやメールのリンク全体は貼らず、画面のエラー文とパラメータの**項目名だけ**（access_token、refresh_token、token_hash、code、type等）を伝えてください。値はすべて秘密です。SQL・Edge Function・Secretの再適用は不要です。
