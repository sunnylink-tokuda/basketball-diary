# 助言の具体化・前のミッションの振り返り（2026-10-20）

作業ブランチ：`feature/chappy-coaching-followup`。mainへのマージ、本番デプロイ、Supabaseデータの変更はこの作業では行いません。

## 変更内容

- 小学5年生のガード向けに、状況判断・オフボール・ディフェンス・声掛けを優先。基本のドリブルを一律に勧めず、次の練習の場面・動作・目標が分かるミッションを1つ提案します。
- 本人の保存済み助言の直近2件を参照。前日・前々日に記録があればその2日を使い、空いている日は直近の利用可能な日を使います。表示には実際の日付を出します。
- 成長比較の候補が2日分なくても、過去の助言を振り返ります。当日の日記に対応する行動の引用があれば「実践の記録あり」「継続中の課題」、確認できなければ「まだ確認できないこと」と本人への質問を表示します。未記載を未実践とは判定しません。本人は次の日記で答えます。過去の日記を編集する必要はありません。
- 継続中・未確認の課題は次の助言にも渡し、原則その中から1つを具体化するよう指示します。痛み・けがや当日の重要な課題を優先します。
- 成長比較の候補は、技術だけでなく判断・オフボール・守備・声掛け・積極性・継続的な取り組みに拡大。「知らせる」と「声を出す」など関連する行動を候補にできます。同じ話題というだけで成長を認定しません。
- 新しい成長チェックでは「成長が確認できたこと」「継続中の課題」「新しい挑戦」を分け、次の成長ポイントも表示。改善未確認なら明記し、比較の根拠自体がなければ成長チェックを表示せず理由を表示します。

## データと安全性

今回の変更に **SQLの実行は不要** です。テーブル、RLS、認証、所有者登録、日記保存処理、再生成の対象日・回数制限、既存回答の不変保護は変更しません。既存の初期設定SQLを本番で再実行しないでください。

新規生成結果のJSONだけに任意の `follow_up` と `growth.new_challenge` が加わります。従来の回答も読み込めます。保存済み助言はそのまま返し、過去の回答を再分析・更新・削除しません。新しい表示を試すために既存データを削除しないでください。既存の10月9日限定再生成も維持します。履歴にその日が含まれ、再生成済みなら本人用の読み取りRPCで最新版を参照します。削除済みの日記は履歴のJOIN対象になりません。

過去の助言は課題の出典として使い、実践・成長の証拠にはしません。日記の引用は空白・句読点等の違いだけを吸収して照合し、否定や数値を変えた引用は認めません。振り返りの実践表示には当日の引用と以前の課題との話題の関連も確認します。意味の解釈すべてを機械的に保証するものではないため、プレビューで実際の回答も確認してください。

過去30日・最大20件・本人のみの読み取りを維持し、モデルへの送信内容から保護者コメント・お小遣い等を除外します。入力本文の予算には前の助言2件の重複分も考慮。OpenAIは1生成につき1回、25秒タイムアウト、`store:false`、日次上限と再試行間隔も従来どおりです。追加の振り返りに必要な出力枠を1,100から最大1,800トークンに増やしています。実際の料金は出力長等によって変わります。

`OPENAI_API_KEY` と `SUPABASE_SERVICE_ROLE_KEY` はEdge Function内の既存Secretだけを利用します。フロントエンド・Vercelの `VITE_*`・GitHubに追加しません。`CHAPPY_ALLOWED_USER_IDS`、JWT検証、所有者確認も維持します。

## デプロイ手順（まずテスト環境）

1. このブランチをチェックアウトし、上記のテスト・ビルドを実行します。
2. 現在の所有者対応表・成長分析・再生成SQLが導入済みの **テスト用Supabaseプロジェクト** を使用し、既存Secretsと許可ユーザーを確認します。新しいキーをコードに記載する作業はありません。
3. CLIが使える環境で `supabase functions deploy --help` を確認してから、対象プロジェクトIDを明示して実行します。

   ```sh
   supabase functions deploy chappy-advice --project-ref YOUR_TEST_PROJECT_REF
   ```

   `supabase/config.toml` の `verify_jwt = true` を維持し、`--no-verify-jwt` は使いません。
4. VercelでこのブランチのPreviewを作成。公開用Supabase URL・anon keyは同じテスト用プロジェクトに合わせます。Edge Functionとフロントエンドの両方を更新します。**プレビューが本番Supabaseを参照している場合、Functionの更新は本番にも影響します。** 安全な分離ができない場合は、共有プロジェクトに先行デプロイせず、本番反映時にまとめて更新してください。
5. テスト用の新しい日記で、前2件の助言に対応する行動がある/ない、異なる言葉の関連行動、比較不足、同じ課題の継続を確認します。過去の保存済み回答が変わらず、ログイン・日記保存・他の機能が動くことも確認します。
6. 確認後にmainへのマージと本番反映を行う場合は、別途承認のうえ、本番プロジェクト向けにFunctionをデプロイし、Vercelも同じコードで更新します。本番の既存日記の再保存や回答の削除は不要で、新しく生成する日から適用されます。

戻す場合は直前のコードのFunctionとフロントエンドを再デプロイします。新しい任意項目は旧コードでは読めない場合があるため、生成済みの新しい形式を読めるよう、このブランチの `validateStoredAdvice` と表示の互換処理は残してください。ロールバックのために保存済みJSONを変更しないでください。
