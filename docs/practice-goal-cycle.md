# 5項目の日記と、前回目標を引き継ぐ仕組み

## 使い方

日付を開き、青い **「5項目の日記を書く」**（保存後は「5項目の日記を編集」）を押します。

1. 今日の練習・試合内容
2. 前回のアドバイスを実践できた？：直近のAI重点目標、できた／少しできた／できなかった、任意のメモ
3. 今日うまくできたこと
4. 今日うまくできなかったこと
5. 次回の目標

前回目標はAI用アカウントへのログイン後に自動取得します。日記が数日・数週間空いていても、対象日より前の有効な目標を参照します。取得に失敗した場合や未ログイン時は「目標なし」と誤表示せず、再確認やログイン案内を表示します。目標が本当にない場合だけ「前回の目標はありません」と表示します。

回答時の目標の日付と文章を3択・メモと一緒に保存します。過去の日記を編集する際には、その日に回答した目標を維持します。別の目標に回答が勝手に付け替わることはありません。

練習時間・チーム・自主練メニュー・試合の数値成績は、従来の記録欄も引き続き利用できます。以前の4項目形式の日記も、従来の欄から閲覧・編集できます。5項目の編集を初めて開いた場合、既存の振り返りを下書きに表示しますが、保存するまではDBを変更しません。「教えてもらったこと」、保護者コメント、お手伝い、お小遣い、目標などはそのまま残ります。

## 保存と互換性

- 日記のJSONに `practiceReflection` を追加。`content/good/improve/next` と `goal_review`（`goal_date/goal/status/memo`）を保存します。
- AI回答は従来の `good/focus/mission/growth/growth_status/follow_up` を維持し、新規生成から `practice_advice`、`priority_goal`、`previous_goal_review` を追加します。`priority_goal` は `mission` と同じ1つの重点目標で、JSONとしてSupabaseへ保存します。
- 新しい画面では、良かったところ／改善ポイント／前回目標の達成状況／具体的な実践アドバイス／次回重点目標の5項目を表示します。保存済み旧回答をこの形に作り直すことはなく、従来の表示を維持します。
- 3択は本人の自己申告として評価します。サーバーで取得した前回目標と日付・文章が一致しない場合や未回答では、達成を断定しません。「できた」だけで客観的な技術向上を認定しません。
- 前回・前々回の目標を最大2件、成長分析の日記を過去30日・最大20件参照。成長評価は判断・オフボール・守備・声掛けを中心に、複数回の記述に裏付けられる変化を重視します。根拠不十分なら評価せず理由を表示します。
- 通常のJSON保存、認証、許可リスト、RLS、所有者登録、保存済み回答の不変保護、10月9日限定の安全な再生成は維持します。日記や旧回答のUPDATE/DELETEを行うマイグレーションはありません。

## 追加SQLと公開順序

`supabase/chappy-goal-cycle.sql` を1回適用します（再適用も可能）。追加するのは読み取り専用の `chappy_previous_goals(uuid,text)` だけです。既存テーブルの列・制約・RLSや保存データを変更しません。

関数は本人の所有者対応表と存在する日記にJOINし、現在・未来・削除済みの日を除外。新しい重点目標、従来のmission、成功した10/9再生成版に対応します。30日制限は設けず、直近最大2件だけを返します。anon/authenticated/PUBLICの直接実行を禁止し、service_roleだけに許可します。Edge FunctionでJWTと許可リストを確認し、クライアント指定のユーザーIDは使用しません。

1. テストとビルドを実行。
2. SQLをマイグレーションとして適用。
3. `chappy-advice` を `index.ts`、`advice.ts`、**`goalCycle.ts`** の3ファイルで再デプロイ（JWT検証有効）。
4. PRをmainへマージし、既存VercelプロジェクトのProductionがReadyになることを確認。
5. 公開URLのHTML/JSと本番の認証拒否・読み取りRPCを確認。

新しいSecretやVercel環境変数は不要です。OpenAIキーとservice role keyはEdge Function内のみで利用します。モデル呼び出し回数・タイムアウト・出力上限・日次予算は従来と同じです。

戻す必要がある場合も日記や回答を削除しません。表示や生成プロンプトを戻す際、すでに保存された新形式を読める `goalCycle.ts` と `validateStoredAdvice` の互換処理は維持してください。新RPCは読み取り専用なので残してもデータを変更しません。

## 検証方法と限界

```sh
npm ci
npm test
npm run build
npm run test:browser
```

ブラウザ検証はPlaywrightを使用します。Linuxでは `/usr/bin/chromium` があれば使い、それ以外は `npx playwright install chromium` で準備するか `PLAYWRIGHT_CHROMIUM_EXECUTABLE` を指定してください。`TEST_ARTIFACT_DIR` でスクリーンショットと結果JSONの保存先を変更できます。

- SQLはPGliteで、長い日数間隔、所有者分離、旧回答/再生成版の目標、削除済み・当日・未来の除外、ブラウザ権限拒否、既存データ不変を検証。
- ChromiumのiPhone相当390×844タッチ画面で、5項目の登録、3択/メモ、4日前の目標の取得、5項目AI表示、ページ更新後の保持、旧日記の編集、保存エラー時の下書き保持、取得エラーからの再試行を検証。
- ブラウザ試験は実際のアプリとSDKを使い、DB/Auth/OpenAIの境界だけをテスト用応答に置換します。本番にダミー日記を作成せず、メール送信や実モデル料金を発生させません。
- 本番ではデプロイと公開ファイル、追加RPC、認証拒否、既存データの内容ハッシュを確認します。本人の認証済みSafari実機での新規入力・実OpenAIの回答内容は、本番利用時の最終確認対象です。端末での実施や実モデル生成を行ったと偽って報告しません。
